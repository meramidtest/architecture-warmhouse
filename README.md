# Warm Home

# Задание 1. Анализ и планирование

### 1. Описание функциональности монолитного приложения

**Управление отоплением:**

- Пользователи могут
  - управлять системой отопления и мониторить температуру в своих домах
- Система поддерживает 
  - подключение новых объектов/домов через специалиста 
  - настройку и регулировку климат-контроля 
  - сбор и передачу данных о температуре

**Мониторинг температуры:**

- Пользователи могуь получать инорфмацию о температуре дома
- Система поддерживает
  - получение информации о температуре
  - доавбеление новых датчиков через специалиста

### 2. Анализ архитектуры монолитного приложения

- Язык программирования: Go
- База данных: PostgreSQL
- Архитектура: Монолитная, все компоненты системы (обработка запросов, бизнес-логика, работа с данными) находятся в рамках одного приложения.
- Взаимодействие: Синхронное, запросы обрабатываются последовательно.
- Масштабируемость: Ограничена, так как монолит сложно масштабировать по частям.
- Развертывание: Требует остановки всего приложения.

### 3. Определение доменов и границы контекстов

Домены:

- Настройка устройств
  - Контексты:
    - Регистрация устройства
      - незарегестрированное устройство
      - credentials устройства
    - Конфигурация настроек
      - сконфигурированное устройство
      - конфигурация устройства

- Управление устройством
  - Контексты:
    - Выполнение команды устройства
      - цель команды, CommandTarget (устройство)
      - команда
    - Программирование устройства
      - цель логики, LogicTarget (устройство)
      - команда логики, LogicCommand
      - логика
    - Получение телеметрии от устройства
      - телеметрия
      - источник телеметрии, TelemetrySource (устройство)

### **4. Проблемы монолитного решения**

Текущее решение не имеет проблем, в случае если:
- В системе не ожидается масштабное увеличение пользователей и нагрузки на систему
- Над системой будет работать малое количество разработчиков, и ресурсы компании ограничены

Так как в целевой системе планируется масштабирование количества пользователей и разработчиков системы, то она имеет следующие ограничение для целевой системы:

- Скорость разработки: в случае значительного увеличения количества разработчиков, вносить изменения станет все сложнее и дольше
- Масштабируемость: при кратном и резком увеличении нагрузки на сервер - скорость отклика уменьшается
- Отказоустойчиовать: при отказе работы какой-либо части системы (монолита или БД), система не работает полностью

# Задание 4. Создание и документирование API

### 1. Тип API

Ниже выбран тип взаимодействия:
- Async API: если сервису не важен статус выполнения запроса другими сервиса, или не важна скорость выполнения запроса
- REST API: все остальные случаи, чтобы не увеличивать сложность реализации

Коммуникация SPA приложение -> Сервис конфигурации:
- Rest API:
  - Запрос на добавление устройства - пользователю важно увидеть результат выполнения как можно скорее
  - Запрос на конфигураци/ устройства - пользователю важно увидеть результат выполнения как можно скорее

Коммуникация SPA приложение -> Сервис управления устройствами:
- Rest API:
  - Запрос на выполнение команды - пользователю важно увидеть результат выполнения как можно скорее
  - Запрос на добавление/изменение программируемой логики: пользователю важно увидеть результат выполнения как можно скорее
  - Запрос на получение телеметрии: пользователю важно увидеть результат выполнения как можно скорее

Сервис конфигурации -> Сервис управления устройствами:
- Async API:
  - Запрос о создании устройства: "сервису конфигурации" не важен статус выполнения запроса

Сервис конфигурации -> IoT шлюз:
- REST API:
  - Запрос на добавление устройства: пользователю важно увидеть результат выполнения как можно скорее


### 2. Документация API

**REST API (Swagger/OpenAPI):**

- [API конфигурации устройств](api-documentation/configuration-api-swagger.yaml) - добавление и конфигурация устройств, получение списка доступных устройств
- [API управления устройствами](api-documentation/management-api-swagger.yaml) - формирование команд управления, получение телеметрии, сохранение и исполнение программируемой логики

# **Задание 6. Разработка MVP**

### **Как запустить и использовать MVP**

**Запуск:**
- Для запуска MVP достаточно выполнить `docker-compose up` в директории [/mvp](./mvp/)
- Все сервисы поднимутся автоматически и будут готовы к работе

**Использование:**
- Для тестирования MVP используйте Postman коллекции из директории [/api-documentation/mvp_postman_collections](./api-documentation/mvp_postman_collections/)
- Доступны коллекции:
  - [Smart Home Configuration API](./api-documentation/mvp_postman_collections/Smart%20Home%20Configuration%20API.postman_collection.json) - для управления конфигурацией устройств
  - [Smart Home Management API](./api-documentation/mvp_postman_collections/Smart%20Home%20Management%20API.postman_collection.json) - для управления устройствами и получения телеметрии
- Все должно работать "из коробки" без дополнительной настройки

**Примечание:**
- В сервисах нет строгой бизнес-логики - они созданы для демонстрации взаимодействия микросервисов, спроектированного на C4 диаграммах
- Основная цель MVP - показать работу архитектуры и коммуникации между сервисами
